# Reckon — Implementation Plan

Repo: `reckon` · Python package: `reckon` · CLI: `reckon`

Corrects the GPS distance inflation in Fitbit TCX exports before they reach
Strava, by rescaling the file's cumulative distance stream to Fitbit's own
stride-fused total.

Named for dead reckoning — estimating distance travelled by integrating motion
rather than by fixing position. Fitbit's stride-based figure is exactly that, and
this tool chooses to trust it over the noisier GPS-derived one. The name is an
admission that the output is a better estimate, not ground truth.

**Stack:** Python 3.14 for development and CI, stdlib only at runtime; the
supported floor is 3.12 and CI runs the full matrix 3.12/3.13/3.14. Terraform for
the AWS deployment.

This originally read "Python 3.12", chosen to match an assumed Lambda runtime.
That was stale — 3.12 is two releases behind and on security-only fixes, and
Lambda has offered newer runtimes for some time. Nothing in the codebase needs a
specific version: there are no runtime dependencies and no version-gated syntax,
and the suite passes identically on all three. **Verify the available Lambda
runtimes at phase 4 and pin only the deploy artefact** — do not let that
constrain local tooling before then.
**Tenancy:** single-user per deployment. Forkers bring their own Fitbit/Strava app
credentials. Do not build multi-tenant auth.

---

## 1. The problem

The Fitbit Charge 5 records a noisy GPS track. Strava sums the distance stream in
the uploaded file, and GPS jitter has a strictly positive bias — every wobble adds
length, none subtracts — so the total inflates by a few percent, growing with
sample count. Fitbit's app shows a shorter figure because it fuses GPS with
stride/accelerometer data, whose error is roughly proportional and partly
self-cancelling.

The fix: keep the GPS geometry, keep Fitbit's total, rescale the distance stream
so the two agree.

---

## 2. Two run modes, one transform

The **only** things that differ between local and AWS are storage and trigger.
Everything from "here is a log ID" to "Strava has the activity" is shared.

| | Local | AWS |
|---|---|---|
| Trigger | CLI invocation, or `--watch` poll loop | Fitbit webhook → SQS |
| Token store | JSON file under `~/.config/reckon/` | DynamoDB |
| Dedupe store | same JSON file | DynamoDB, TTL 90d |
| Retry | none, fail loudly | SQS + DLQ |
| Offline mode | yes — file in, file out, no API | n/a |

Enforced by a port/adapter boundary. `reckon.core` imports nothing but stdlib.
`reckon.pipeline` depends on abstract stores, never on boto3. Only
`reckon.stores.dynamo` and `reckon.aws` may import boto3, and nothing imports
*them* except the Lambda entry points. Add a test that asserts this — walk the
AST of `core/` and `pipeline/` and fail on a boto3 import. Layering violations
are silent otherwise.

## 4. CLI surface

```
reckon rescale IN.tcx --distance 10.2km -o OUT.tcx   # offline, no network
reckon fetch LOG_ID [--raw]                          # Fitbit -> stdout/file
reckon sync [--since DATE] [--dry-run]               # full pipeline, local store
reckon watch [--interval 900]                        # poll loop
reckon analyse [--corpus training-data/]             # factor distribution
reckon auth fitbit | strava                          # OAuth dance
```

`rescale` is the one that must work with no credentials, no network and no config
— it is how the transform gets validated and how anyone else evaluates the project
in thirty seconds.

`--distance` accepts `10.2km`, `6.3mi`, or a bare number meaning metres
(`10200`). Case-insensitive, no space before the unit. Reject anything else with
a message showing the three accepted forms.

`fetch` without `--raw` returns the *rescaled* TCX, using the distance from the
activity's summary as the target; `--raw` returns Fitbit's bytes untouched.

`--dry-run` on `sync` should do everything except the Strava POST and print the
before/after totals and factor.

## 5. The transform (build and test this first)

`reckon.core.rescale.rescale_tcx(tcx_bytes, target_distance_m, *, tolerance=0.2) -> RescaleResult`

Return a result object carrying the modified bytes plus `gps_total_m`,
`target_m`, `factor`, `trackpoint_count`, `warnings` — the CLI and the analyse
command both need those numbers, not just the output file.

1. Parse with `xml.etree.ElementTree`. Register the TCX namespace
   (`http://www.garmin.com/xmlschemas/TrainingCenterDatabase/v2`) and the activity
   extension namespace so output round-trips cleanly.
2. Read the final `Trackpoint/DistanceMeters` — the GPS-derived total.
3. `factor = target_distance_m / gps_total_m`
4. Multiply in place: every `Trackpoint/DistanceMeters`, every
   `Lap/DistanceMeters`, `Lap/MaximumSpeed`, any `Extensions/TPX/Speed`, and any
   `Activity`-level totals present.
5. Serialise preserving the default namespace — ElementTree emits `ns0:` prefixes
   unless told otherwise. Known papercut, test for it explicitly.

**Temporal invariant — timestamps are never touched.**

The transform multiplies distance and speed values only. Every time-bearing
element round-trips byte-identical:

- `Activity/Id` (the ISO8601 activity start)
- `Lap@StartTime` and `Lap/TotalTimeSeconds`
- every `Trackpoint/Time`

Start, end, elapsed time and date are therefore preserved exactly. Assert this
rather than assume it: `test_rescale.py` should extract the ordered list of every
timestamp in the file pre- and post-transform and require equality. Cheap, and it
catches regressions if the transform is ever extended.

Two consequences worth understanding, neither caused by the rescale:

- **Timezone.** TCX timestamps are UTC with a `Z` suffix; Strava derives the
  displayed *local* start time from the activity's starting coordinates. Since the
  geometry is preserved, local time stays correct. This would break if GPS were
  ever stripped.
- **Moving time may shift a little.** Distance shrinks and time does not, so
  instantaneous speed drops by `factor` at every point. Strava computes moving
  time itself by thresholding speed, so points already hovering near the
  stopped/moving boundary — a road crossing, a stile — can tip to counting as
  stopped. Elapsed time is unaffected; moving time may move by a few seconds.

**Guards, each needing a test:**

- No `DistanceMeters`, or final value 0 → return unmodified with a warning. Do
  not fabricate a stream.
- No `Position` elements (indoor activity) → skip the activity entirely.
- `abs(factor - 1) > tolerance` → refuse by default; a large discrepancy is more
  likely a bad Fitbit summary than a bad track. Configurable
  `abort` | `clamp` | `proceed`.
- Non-monotonic input distance → warn, proceed (monotonicity survives
  multiplication).

**Outcomes: deterministic skips are not failures.**

The pipeline maps every activity to exactly one of three outcomes, and the
distinction drives retry behaviour everywhere downstream:

- `uploaded` — Strava accepted it; record the activity id.
- `skipped(reason)` — a *deterministic* result: no GPS, no distance stream,
  factor outside tolerance with `abort` configured. Record it in the processed-log
  store with the reason, delete the queue message, do **not** retry. Retrying
  cannot change the input, and letting these raise in AWS mode would burn three
  receives and poison the DLQ with activities that can never succeed.
- raised exception — a *transient* fault: network, 429, 5xx, throttling. Let it
  propagate so SQS retries and, if persistent, the DLQ alarm fires.

`ProcessedLogStore` therefore stores a status (`uploaded` | `skipped` | `failed`)
and a reason, not a bare seen-marker. `reckon sync` prints the same three-way
outcome per activity.

## 6. training-data/

Gitignored directory holding **your own** raw Fitbit exports, used to validate and
calibrate the transform. Not committed, for two reasons: the files are large, and
a raw TCX is a precise record of where you live and when you leave the house.

`.gitignore`:
```
training-data/*
!training-data/.gitkeep
!training-data/README.md
```

Contents: `NNNN.tcx` alongside `NNNN.json` (the Fitbit activity summary, or just
`{"distance_m": 10200}` hand-written from the app display).

Two things consume it:

- `tests/test_corpus.py` — parametrised over whatever is present, `pytest.skip` if
  empty so CI and forkers stay green. Asserts the transform runs clean, the factor
  falls in a plausible band, and the temporal invariant holds on every file.
- `reckon analyse` — reports factor mean, stdev, and range across the corpus.
  `--plot` writes `docs/factor-distribution.svg` as **hand-emitted SVG** — a
  histogram is a few dozen `<rect>` elements and this project writes XML for a
  living. No matplotlib; the zero-dependency property in §3 holds for the CLI too.

Two temporal measurements belong in `analyse` too, because the corpus is the only
place to find out how much they matter in practice:

- **Start-time lag.** With `includePartialTCX=true`, if Fitbit lost GPS lock at
  the start the first trackpoint can post-date the true activity start, so
  Strava's start time lags what the Fitbit app shows. Pre-existing Fitbit
  behaviour, not something the rescale introduces — but report
  `first_trackpoint_time - activity_summary_start_time` per file so the frequency
  and size are known.
- **Moving-time delta.** Estimate moving time before and after the rescale using
  a fixed speed threshold, and report the difference. Confirms the effect is
  seconds rather than minutes on real runs.

That analysis is worth doing early and is genuinely informative.

- **Strava reports the trackpoint distance stream**, to within 0.21% and often far

### Dead reckoning is not the mechanism

§1 explains the correction as GPS fused with **stride cadence**, and the project
is named for it. The cycling files falsify that as a complete account.

There are no strides on a bicycle, yet Fitbit's total still came in below the GPS
stream on both rides — 198 m and 54 m, factors 0.9797 and 0.9943. Whatever Fitbit
does to produce its total, it is not primarily stride-based dead reckoning,
because it does the same thing for an activity with no stride signal at all.

**What the corpus supports instead: Fitbit smooths, Strava sums raw.** Define
wiggle as full-resolution path length over the same path decimated to one fix per
5 s — real movement is smooth at that scale, GPS jitter is not, so the ratio
isolates high-frequency noise from genuine cornering.

Across the eight complete tracks wiggle correlates with inflation at **r = +0.859,
Spearman rho = +0.881**, well ahead of duration (+0.75), distance (+0.55) and
speed (-0.42). It has strengthened with every file added — +0.76 at n = 6, +0.81
at n = 7, +0.86 at n = 8 — which is not how a spurious correlation usually
behaves. It has also made one genuine out-of-sample prediction: before the second
ride's factor was known, wiggle was predicted at 1.005-1.015 from its 0.58%
inflation and measured 1.014.

Two limits keep this a hypothesis rather than a finding:

- **It fails to separate the two long runs.** Both measure wiggle 1.103; their
  inflations are 6.04% and 12.15%. Something else is operating there.
- **The excess-to-inflation ratio is not constant** — 1.4% excess against 0.58%
  inflation on one ride, 2.5% against 2.07% on the other. Wiggle orders
  activities well; it does not measure the factor.

Speed is best read as a proxy for smoothness rather than a cause: bicycles track
cleanly, and cleanliness is what correlates.

**Consequences.** None for the transform, which never depended on why Fitbit's
total is better. Two for the documentation, both now done:

1. `README.md` §"How it works" and this section state only what is supported:
   Fitbit's total is demonstrably not a raw GPS sum, Strava's demonstrably is, and
   the difference tracks high-frequency noise. Do not assert a filter design that
   has not been observed, and do not reintroduce the stride-fusion explanation.
2. The name and the `dead-reckoning` keyword in `pyproject.toml` are imprecise.
   Not worth renaming a project over, but do not lean on the metaphor in new prose.

**`Sport` is expressible for runs and rides, not for walks.** Runs export as
`Running`, both rides as `Biking`, both walks as `Other` — TCX v2 permits only
those three. So phase 6 can trust `Running` and `Biking` directly and only needs
the Fitbit activity summary to disambiguate `Other`.

**A fixed fallback factor is not defensible.** Over the eight complete tracks the
factor ranges 0.8916-0.9943, mean 0.9511, stdev 0.0351. Where the target total is
unavailable, skip the activity; do not substitute a guessed factor. **Do not use
wiggle to synthesise one either** — it is a correlate, not a measurement, and the
two long runs show where that would go wrong.

**The no-GPS guard is reachable, and is now covered by real data.** It was
briefly recorded here that Fitbit likely does not export TCX for a GPS-less
activity, reasoning that TCX is a track format. That was wrong. A **yoga**
session exports as TCX and syncs to Strava:
1867 trackpoints carrying only `Time` and `HeartRateBpm`, zero `Position`
elements, no `Trackpoint/DistanceMeters`, and `Lap/DistanceMeters` of `0.0`.

`rescale` handles it correctly — both warnings fire, exit 0, and the output is
**byte-identical** to the input rather than a re-serialisation, which is what
`_unchanged()` exists to guarantee. Strava displays it as 0 km, matching
`Lap/DistanceMeters`, and its elapsed time still matches the trackpoint span to
the second. The cross-app rules hold even for an activity with no distance.

**`Sport="Other"` carries no information at all.** It now spans a 5.26 km walk
and a stationary yoga session. Phase 6 must always consult the Fitbit activity
summary for `Other`; there is no defensible fallback. `Running` and `Biking`
remain trustworthy.

### Three defects the corpus exposed — all fixed

1. **`trackpoint_count` reported 0 for a file with 1867 trackpoints.** It
   accumulated only over *scaled* activities, so every skip guard zeroed it, and
   the CLI printed a flatly false `0 trackpoints`. It now counts every trackpoint
   in the file, scaled or not: the number describes the input, not what the
   transform touched. Message reworded to
   `N trackpoints, nothing to rescale, file written unchanged`.

2. **`--distance` was mandatory but sometimes meaningless.** Rescaling the yoga
   file required an arbitrary `--distance 1000` that was then ignored. It is now
   optional and defaults to the file's own `Lap/DistanceMeters` — which the
   corpus proved *is* the target on every activity type. `reckon rescale FILE`
   is the whole command; `--distance` remains as an override and reports itself
   as `(given)` versus `(from file)`.

   The no-GPS guards resolve *before* any target is needed, so a file with
   nothing to scale round-trips byte-identically whether or not a target exists.
   An explicitly supplied bad target is still rejected eagerly — that is a caller
   error, and is never second-guessed. `MissingTarget` covers "asked to read the
   target from the file, and the file has none".

3. **The transform was not idempotent** — found while fixing (2), and *created*
   as a hazard by it. `Lap/DistanceMeters` was in `_SCALED_TAGS`, so the first
   pass multiplied Fitbit's own total by the factor derived from it. With an
   explicit target that was harmless; reading the target from the file made a
   second run shrink the distance again, silently: 15229 -> 14362 -> 13544.

   `Lap/DistanceMeters` and `Trackpoint/DistanceMeters` mean different things and
   now take different factors. The lap total is the authority — the stream is
   moved to meet it, and the lap value survives untouched when it *is* the
   target. With an overriding `--distance` the lap totals move to the new target
   instead, keeping their proportions across multiple laps, so the output is
   self-consistent either way. Verified across all ten corpus files: lap
   preserved, `Lap == stream final`, and a second pass byte-identical.

### Correcting numbers must never mean dropping activities

The owner's requirement (2026-08-27): *"I want Strava to record all my sports, I
just want to make the numbers more accurate."*

That splits a distinction §5 currently conflates. The three-way outcome uses
`skipped(reason)` for no-GPS, and in the phase-5 pipeline that reads as *do not
upload*. It must not. **"Cannot correct" and "do not upload" are separate
decisions.** A yoga session is uncorrectable and must still reach Strava
unchanged; only a genuinely unprocessable file should be withheld. Rename or
split the outcome before building the pipeline — `passed_through` versus
`withheld` is the real distinction.

The partial-GPS walk is the one case that needs thought: it is correctable in
principle but must not be corrected. It should still upload, uncorrected.

### Strava learns sport type from somewhere other than the TCX

Observed (owner, 2026-08-27): Strava labels these activities correctly despite
`Sport="Other"` on walks and yoga. Since TCX v2 carries only `Running`,
`Biking` and `Other`, the type cannot have come from the file — the native
Fitbit-to-Strava integration must pass it through the API alongside the upload.

This matters for phase 6 and is **unresolved**. Reckon edits distances and
speeds only and never touches activity type, so it cannot make typing worse. But
a Reckon-uploaded activity goes to Strava as a file upload, which has only the
TCX `Sport` value to go on — so walks and yoga would arrive as `Other` where the
native sync got them right. Before building the uploader, establish where the
native integration sources the type, and set Strava's `sport_type` explicitly
from the Fitbit activity summary rather than relying on the file.

**Near-no-op corrections are normal and must stay supported.** The second ride's
factor is 0.9943, a 54 m change over 9.3 km. `rescale` handles it correctly. Do
not add a "too small to bother" short-circuit; a 54 m correction is still the
difference between the two apps agreeing and not.

### Partial GPS: the case where rescaling is wrong

One walk in the corpus is its most
valuable file, because it is the one that must **not** be transformed.

Fitbit held no GPS lock for the first 383 s. The distance stream does not lag —
it does not exist until +383 s, where it restarts from `0.00`. So
`Lap/DistanceMeters` is 2105.66 m (the whole walk, stride-fused, and what Google
Health shows) while the stream ends at 1583.83 m (post-lock only, and exactly
what Strava shows, 1.58 km). The 521.83 m difference is real distance GPS never
recorded.

- **The factor is 1.3295 — above 1.** Every other file in the corpus sits below.
  The transform is being asked to *inflate*, which is a different operation from
  the one it was designed for.
- **Applying it would fabricate.** Scaling 1583.83 m of geometry up to 2105.66 m
  attributes pre-lock distance to post-lock ground. The output looks plausible
  and is wrong.
- **The guard catches it.** `rescale` aborts by default, exit 1. This is the
  tolerance check doing exactly its job on real data, and is the strongest
  argument yet for keeping `abort` as the default.
- **Strava counted the positionless prefix as stopped time.** Moving 16:18 vs
  elapsed 22:42 — a 384 s gap against the 383 s GPS-less prefix.
- **The cause of the lock failure is not in the file.** The opening block samples
  every 2.0 s against 1.0 s once position appears, which looks like acquisition
  rather than a response to standing still. Within the recorded window the track
  is continuous: no pause (largest gap between trackpoints is 3 s), strictly
  time-ordered, and per-minute net displacement never drops below 63 m, including
  the final minute. Do not infer user behaviour from this file — the owner
  reports standing still near the end of the walk, and no such period is visible
  in the recorded track, so the recording evidently stopped before it.

Two consequences for the build:

1. **The tolerance error message gives harmful advice here.** It suggests
   "check the target distance, or pass `--on-tolerance clamp|proceed`", and
   `proceed` produces the fabricated file. For a partial track both remedies are
   wrong; the correct action is to skip. The message assumes a mismatched target,
   which was the only failure mode §5 anticipated.
2. **Partial GPS is detectable, not merely suspected.** A distance stream that
   begins at 0.00 well into the activity, with no `Position` before it, is an
   unambiguous signature. `rescale` should name that cause rather than report a
   bare factor breach, and phase 5 must treat it as a deterministic
   `skipped(partial_gps)` — never a retry. This supersedes the §"Start-time lag"
   note, which framed the `includePartialTCX` problem as a start-time cosmetic
   issue; it is a correctness issue.



`scripts/anonymise.py` promotes a training file to a committable fixture: shift
all coordinates by a constant offset, rebase timestamps to an epoch, strip device
serial and user ID. That is how `tests/fixtures/` gets populated.

**Validate before writing any infrastructure.** Export a real TCX, run
`reckon rescale`, check the output total against the Fitbit app.

## 7. Testing strategy and coverage

Target: 100% line and branch across `src/reckon/`, enforced from the first commit.

**Set the gate at 100 on day one.** Retrofitting coverage onto existing code is
expensive; holding it from the start is nearly free, because it changes what gets
written rather than what has to be gone back over. `fail_under = 100` in
`pyproject.toml` from phase 1, not phase 8.

```toml
[tool.coverage.run]
branch = true
source = ["src/reckon"]

[tool.coverage.report]
fail_under = 100
show_missing = true
skip_covered = true
exclude_lines = [
  "pragma: no cover",
  "if TYPE_CHECKING:",
  "^\\s*\\.\\.\\.$",
  "if __name__ == .__main__.:",
]
```

Run via `pytest-cov` (`pytest --cov --cov-branch`). Do not set `parallel = true`
— it requires a `coverage combine` step and, forgotten, yields empty reports and
a baffling gate failure; single-process pytest has no need of it.

Rule on `# pragma: no cover`: every use carries a comment justifying it. If the
justification is "hard to reach", that is a design smell, not a pragma.

### Design choices that make the target reachable

These are architecture decisions to take now, not test-time tricks applied later.

**One network seam.** All urllib usage lives in a single function in
`clients/http.py`, behind `Transport = Callable[[Request], Response]`.
`fitbit.py` and `strava.py` accept a `Transport` at construction and never import
urllib themselves. Above the seam, tests inject a canned-response fake — no mock
library, no patching. This matters given the zero-dependency stance: there is no
stdlib equivalent of `responses`, and monkeypatching `urllib.request.urlopen` is
brittle.

**Test the seam itself against a real server.** `http.py` is exercised against
`http.server.ThreadingHTTPServer` on a loopback port in a pytest fixture. That
genuinely covers 429 handling, redirects, timeouts, connection reset and chunked
bodies rather than a mock's idea of them. Around 40 lines of fixture, and it is
the one module that cannot be faked.

**Inject clock and sleep.** Token expiry, backoff and TTL all read the clock. Pass
`now: Callable[[], float] = time.time` and `sleep: Callable[[float], None] =
time.sleep` into clients and stores; tests supply a controllable clock and a
recording no-op sleep. Without this the retry branches are either untestable or
slow, and expiry logic can only be tested by waiting.

**Seed or inject jitter.** Backoff jitter uses an injected `random.Random`
instance, never the module-level functions.

**No import-time side effects.** `boto3.client(...)` at module scope runs on
import and needs credentials and a region — it fails in CI and distorts coverage.
Construct lazily inside a function, or accept the client as a parameter.

**Thin handlers.** `aws/receiver.py` and `aws/worker.py` parse the event,
delegate, format the response. No business logic. Their coverage is then a handful
of dict fixtures rather than a simulated AWS environment.

**Protocols over ABCs.** `stores/base.py` uses `typing.Protocol` with `...`
bodies — excluded by config, leaving no unreachable `raise NotImplementedError`
lines to explain away.

**Do not write unreachable defensive branches.** `else: raise
AssertionError("unreachable")` is uncoverable by definition. Prefer making the
state impossible by construction: exhaustive enum handling, frozen dataclasses
validating in `__post_init__`.

### Fixture generation

Branch coverage of the §5 guards needs TCX inputs that mostly do not occur in real
data: missing `DistanceMeters`, zero final distance, absent `Position`,
non-monotonic distance, factor beyond tolerance, single trackpoint, empty track,
multiple laps, multiple `Activity` elements in one file.

Hand-writing a dozen XML files is unmaintainable. `tests/builders.py` is a small
TCX builder taking keyword parameters and emitting bytes; each guard then becomes
a one-line parametrised case. The anonymised files in `tests/fixtures/` serve a
different purpose — proving the parser copes with what Fitbit actually emits.

### What is measured, and what is not

- `src/reckon/` — 100% line and branch, gated in CI.
- `scripts/` — excluded from measurement, and kept trivial to earn that. All
  logic (authorisation URL construction, code exchange, subscription creation)
  belongs in `clients/` where it is testable; `scripts/` holds argparse plumbing
  only. A script past ~30 lines means logic is in the wrong place.
- `deploy/terraform/` — coverage does not apply. Gate with `terraform fmt -check`,
  `terraform validate`, optionally `tflint`.

### Coverage is necessary, not sufficient

100% line and branch means every line ran, not that any assertion would have
caught it being wrong. For a transform whose entire purpose is the correctness of
a multiplication, that gap matters.

Run `mutmut` against `core/` only, as a separate non-blocking CI job. A surviving
mutant — `*` become `/`, `>` become `>=`, a boundary shifted by one — means the
tests execute the line without constraining its behaviour. `core/` is small, pure
and fast, which is exactly where mutation testing pays; running it tree-wide would
be slow and mostly noise.

## 8. Critical API details

These fail silently if got wrong. Verify each against current docs during
implementation. **On divergence, the live API wins**: prefer observed behaviour,
and update this plan file to match rather than silently deviating from it.

### Fitbit

- **Scopes:** `activity` and `location`. Without `location` the TCX has no GPS.
- **Refresh tokens are single-use and rotate on every refresh.** Losing one forces
  a manual re-auth. The DynamoDB conditional write on a version attribute (or an
  exclusive file lock locally) is the *primary and sufficient* guard: persist the
  new pair *before* using the new access token, and a loser of the race re-reads
  and proceeds with the winner's tokens. Concurrency limiting (§9) is best-effort
  reduction of contention, not the correctness mechanism.
- **The webhook notification does not contain the activity log ID.** Body is a
  JSON array of `{collectionType, date, ownerId, ownerType, subscriptionId}`. The
  worker must call
  `GET /1/user/-/activities/list.json?afterDate={date}&sort=asc&limit=20&offset=0`
  and diff against the processed-log store. `date` is in the user's Fitbit
  timezone; to cover the midnight boundary, query from the day *before* the
  notification date — the dedupe store makes the overlap harmless. Verify this
  edge during implementation.
- **Signature:** `X-Fitbit-Signature` is `base64(HMAC-SHA1(raw_body, client_secret + "&"))`.
  Use `hmac.compare_digest` and the *raw* body bytes, not a re-serialised dict.
- **Units:** the summary `distance` field follows the `Accept-Language` header.
  Send `en_GB` explicitly on every call and assert `distanceUnit`.
- **TCX:** `GET /1/user/-/activities/{logId}.tcx?includePartialTCX=true` with
  `Accept: application/vnd.garmin.tcx+xml`.
- Rate limit 150/hour/user. Back off on 429.

### Strava

- Refresh token does **not** rotate (unlike Fitbit). Access token lives 6h.
  Scope `activity:write`.
- `POST /api/v3/uploads` — multipart: `file`, `data_type=tcx`, `name`,
  `description`, `external_id`, `sport_type`.
- **Set `external_id` to the Fitbit log ID.** Strava dedupes on it — a second
  idempotency layer independent of your own store.
- Upload is asynchronous: poll `GET /api/v3/uploads/{id}` until `activity_id` is
  set or `error` is non-null. Locally, a bounded retry loop is fine. In Lambda,
  delayed SQS re-enqueue (`DelaySeconds=20`, backing off) — never `sleep`.
- Limits: 200 per 15 min, 2000/day. Read `X-RateLimit-Usage`.

## 9. AWS deployment

```
Fitbit ──POST──► Lambda receiver ──► SQS ──► Lambda worker ──► Strava
                 (Function URL)      +DLQ      │
                                               └──► DynamoDB (tokens, dedupe)
```

- **receiver:** `GET ?verify=CODE` → 204 if it matches the configured code, else
  404 (one-time subscriber handshake). `POST` → verify signature, enqueue, return
  204. No real work; Fitbit expects a fast ack.
- **worker:** SQS-triggered, timeout 60s, 256MB, `batch_size = 1`. Concurrency is
  bounded with `scaling_config { maximum_concurrency = 2 }` on the event source
  mapping — **not** `reserved_concurrent_executions = 1`. Reserved concurrency 1
  has a known failure mode with SQS: the poller scales independently, throttled
  deliveries expire their visibility timeout, receive counts climb, and healthy
  messages poison into the DLQ. Correctness under the residual concurrency of 2
  comes from the token CAS (§8), which must be right regardless.
- **Message schemas** — the queue carries exactly two shapes:
  ```json
  {"type": "notification", "received_at": "<iso8601>", "body": "<raw webhook body, string>"}
  {"type": "upload_check", "strava_upload_id": 123, "fitbit_log_id": 456, "attempt": 1}
  ```
  The receiver wraps; the worker discriminates on `type`. `upload_check` is
  re-enqueued with `DelaySeconds` 20, 40, 80… and a **cap of 5 attempts**; on the
  final attempt with the upload still processing, mark the log `failed` in
  DynamoDB and stop — no unbounded polling, no DLQ entry for a slow Strava.
- **DynamoDB:** single table, on-demand. `TOKEN#fitbit`, `TOKEN#strava`,
  `LOG#{logId}` carrying `{status: uploaded|skipped|failed, reason, strava_activity_id}`
  with TTL.
- **SSM Parameter Store SecureString** for client IDs/secrets and the webhook
  verification code. Free; mention Secrets Manager as the alternative.
- **Terraform:** `required_version = ">= 1.10"` — the floor is imposed by S3
  native state locking (`use_lockfile = true`); no legacy DynamoDB lock table.
  Provider pinned `~> 6.0`. `backend.tf.example` only. Separate least-privilege
  role per Lambda: receiver gets SQS send + SSM read; worker gets SQS
  receive/send/delete, DynamoDB on the one table, SSM read. Function URL
  `authorization_type = "NONE"` — the HMAC check is the auth, say so loudly in
  the README. SQS visibility timeout ≥ 6× worker timeout, `maxReceiveCount = 3`
  → DLQ. Log retention 14 days, CloudWatch alarm on DLQ depth > 0.
- Within the AWS free tier; realistic steady-state cost is pence a month.

## 10. Build order

Each phase green before the next.

"Green" includes the coverage gate. `fail_under = 100` is configured in phase 1
and never lowered — if a phase cannot reach it, that is information about the
design, not a reason to relax the threshold.

1. **Scaffold** — layout, pyproject (including the coverage config from §7),
   Makefile, ruff, pytest, MIT, `.gitignore` including `training-data/`. CI runs
   and the gate passes trivially on an empty tree.
2. **Core** — draft README §1–7 *first* (see §11), then `tcx.py`, `rescale.py`,
   `reckon rescale` CLI subcommand, `builders.py`, `test_layering.py` (it passes
   trivially until there is something to violate — which is the point), unit
   tests. Validate against real exports by hand.
   **Stop here until the numbers are right.**
3. **Corpus** — `training-data/`, `test_corpus.py`, `reckon analyse`,
   `anonymise.py`, commit the resulting fixtures. Add the `mutmut` job over
   `core/` here, while `core/` is the whole codebase and the signal is clearest.
   Produce the README's before/after table and the factor-distribution plot from
   real corpus output, not invented numbers.
4. **Clients** — draw `upload-lifecycle.puml` first, then `http.py` with the
   `Transport` seam and its loopback-server tests, then `fitbit.py`, `strava.py`,
   `authorize.py` against `fakes.py`. **Acceptance test for the whole premise:**
   upload one rescaled file by hand and assert the resulting Strava activity's
   distance equals the target within rounding. If Strava recomputes from the
   coordinates instead of honouring the stream, everything downstream is moot —
   stop and reassess before phase 5.
5. **Stores + pipeline** — draw `token-refresh.puml` first and settle what the
   losing CAS branch does. Then protocols, `file.py`, `pipeline.py`,
   `reckon sync`. This is a fully working local tool; tag it.
6. **AWS** — `dynamo.py` (tested under moto, including the conditional-write CAS
   path with a simulated race), thin handlers with the §9 message schemas.
7. **Terraform** — deploy, register the subscriber URL, run `subscribe.py`.
8. **Docs and CI** — finish the README (setup, AWS, alternatives, FAQ), write
   `ARCHITECTURE.md`, record `docs/demo.tape` and `make demo`, Mermaid diagram in
   the README, `deployment.puml` and `make diagrams`, then ruff + pytest with
   coverage gate + `terraform fmt -check` + `validate` + diagram drift check
   (`make diagrams && git diff --exit-code`), mutation job non-blocking.

## 11. Documentation

Two files, with a deliberate division of labour: README answers "should I use
this and how", ARCHITECTURE answers "how do I change it".

### README structure

Ordered by who reads how far. Most visitors read the first screen and leave, so
the first screen must carry the decision.

1. **Name, one-line description, badges.** `Reckon — corrects Fitbit's GPS
   distance inflation before uploading to Strava.` Four badges only: CI status,
   coverage, licence, Python version. Coverage earns its place here because §7
   makes it a real claim; download counts and social badges do not.
2. **The problem, in three sentences and one table.** Before/after on a real run:
   what Fitbit showed, what Strava showed, what Reckon produces. This is the
   single most persuasive thing in the document — anyone with the same complaint
   recognises their own numbers.
3. **Demo GIF** of `reckon rescale` running. Scripted with
   [vhs](https://github.com/charmbracelet/vhs), tape committed to `docs/`, GIF
   regenerated by `make demo`. Never hand-record; it rots and cannot be updated.
4. **Quickstart** — install, then the one offline command, then the output. No
   credentials, no config, no AWS. Someone must be able to evaluate the whole
   premise in under a minute.
5. **How it works** — the dead reckoning explanation. GPS jitter has a one-way
   positive bias; stride-based distance drifts but does not systematically
   inflate; the tool takes the total from the latter and the geometry from the
   former. Short, and the most interesting content in the repo.
6. **Honest limits**, as its own section rather than scattered caveats:
   - it corrects a systematic bias, it does not recover ground truth
   - splits all shift proportionally; the pace *shape* is preserved
   - timings, dates and route are unchanged, but Strava's *moving* time may
     differ by seconds since it derives that from speed
   - it is only as good as Fitbit's own total
7. **Full usage** — the CLI table from §4.
8. **Fitbit and Strava setup** — app registration, scopes, OAuth. Inside
   `<details>`; irrelevant to anyone using offline mode.
9. **AWS deployment** — inside `<details>`, with the Mermaid architecture diagram.
   Leads with the warning to disable the native Fitbit→Strava connection first,
   the note that the Function URL is public and HMAC-protected, the cost estimate,
   and teardown steps.
10. **Alternatives** — FitToStrava, SyncMyTracks, Health Sync, RunGap, and the
    fact that tapiriik has no Fitbit connector. Naming the competition costs
    nothing and lets people who want a click-and-forget bridge self-select out
    before they waste an evening.
11. **FAQ** — why the distance still differs, whether times change, why TCX rather
    than FIT, whether this risks the Strava account (no: documented public API),
    what happens with indoor runs.
12. **Contributing, licence.**

Use `<details>` blocks for the setup and AWS sections. The single biggest
structural risk for this README is that the AWS material buries the CLI, which is
what most readers actually want.

**Do not** add: a project logo, emoji section headers, contributor avatars, star
history, a manual table of contents (GitHub generates one from headings), or
badges beyond the four. Each is common in the awesome-readme examples and each is
optimised for attracting stars rather than for someone with this specific problem
finding their answer.

### ARCHITECTURE.md

Per matklad's argument for the file: a newcomer's problem is not understanding
the code, it is knowing where to look. Contents:

- **Source map** — one line per module saying what it owns.
- **The invariants**, stated as rules a change must not break: `core/` imports
  stdlib only; `pipeline/` never imports boto3; all network I/O passes through
  the single `Transport` seam; timestamps are never modified. `test_layering.py`
  enforces the first two; the rest are conventions and need writing down.
- **Why local and AWS share a pipeline** and what specifically differs (the §2
  table).
- **Design decisions with their rationale**: stdlib-only and what it buys;
  rescale rather than Kalman smoothing or map matching, and when that choice would
  be worth revisiting; worker concurrency 1 as token-rotation protection.
- **Links to the rendered sequence diagrams**, placed next to the prose they
  illustrate rather than collected in a gallery at the end.

### Diagrams: Mermaid in the README, PlantUML in the docs

Split by one practical constraint — GitHub renders Mermaid inline and does not
render PlantUML at all. Anything embedded in the README must therefore be Mermaid
or a committed image.

**Mermaid** — the single high-level architecture diagram in the README's AWS
section. Diffs in git, needs no toolchain, never goes stale against the code.

**PlantUML** — `docs/diagrams/*.puml`, rendered to committed SVG by
`make diagrams`, linked from `ARCHITECTURE.md`. Worth the extra toolchain for
three things Mermaid handles badly or not at all:

- `token-refresh.puml` — the Fitbit rotating-refresh-token race. Single-use token
  plus DynamoDB conditional write means there is a losing branch, and an `alt`
  fragment showing *CAS succeeds → persist new pair* against *CAS fails → re-read
  and proceed with the winner's tokens* documents the invariant far better than
  prose. Draw the **concurrent** case explicitly — §9's `maximum_concurrency = 2`
  means two workers can genuinely race, so the diagram shows how the race is won,
  not that it is prevented. Mermaid's nested `alt`/`opt` handling, activation bars
  and notes are weak; PlantUML's are not.
- `upload-lifecycle.puml` — webhook → 204 → SQS → worker → `POST /uploads` →
  delayed re-enqueue → `GET /uploads/{id}`, looping until `activity_id` or
  `error`. Several participants, a loop with an exit condition, and a deliberate
  respond-before-work step at the front.
- `deployment.puml` — using `aws-icons-for-plantuml`, which has no Mermaid
  equivalent. More accurate and more legible than boxes for a Terraform stack.

Skip C4-PlantUML. Two Lambdas and a queue do not need context/container/component
layers.

**Toolchain:** render via the `plantuml/plantuml` Docker image rather than
installing Java and Graphviz locally. Docs-time only; it never touches the Lambda
package, so the zero-runtime-dependency property in §3 is unaffected. Add a CI
step that regenerates the SVGs and runs `git diff --exit-code`, the same
discipline as `terraform fmt -check` — it catches diagrams that have drifted from
their source.

**Draw two of these before writing the code they describe.** `token-refresh.puml`
belongs at the start of phase 5 and `upload-lifecycle.puml` at the start of phase
4. Sketching the refresh sequence is how you decide whether the losing CAS branch
retries, aborts, or deadlocks — a question worth answering on a diagram, because
the failure it guards against only appears under concurrency you will not
reproduce locally.

### Write the README first

Preston-Werner's readme-driven development applies well here. Draft §1–7 of the
README during phase 1, before `rescale.py` exists. The CLI surface in §4 is a
guess until it has been written as documentation, and that draft is the cheapest
place to discover that a flag is awkward or a subcommand is misnamed.
